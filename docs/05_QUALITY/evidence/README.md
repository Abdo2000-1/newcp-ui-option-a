# Evidence System

The selected package and acceptance checklist require evidence links for passing checks, but no submission naming or retention policy was available. This directory is therefore a design and control point, not a collection of fabricated reports.

## Recommended structure

Create subdirectories only when real artifacts exist:

```text
evidence/
  traceability/       # requirement-to-test/demo mapping
  tests/              # raw reports and concise summaries
  api/                # OpenAPI lint/contract behavior
  accessibility/      # keyboard, semantics, responsive results
  build/              # lint, typecheck, build, Docker, SonarQube
  demo/               # sanitized screenshots, recordings, scripts, baselines
  review/              # review findings and acceptance decisions
  ai/                 # sanitized AI usage references when required
```

## Artifact rules

Every artifact should state the requirement/task ID, environment, procedure or command, date, result, reviewer, and limitations. Keep secrets, PHI, customer data, production tokens, and unsanitized logs outside the repository. Use stable filenames and link the artifact from the traceability matrix or task breakdown.

## Evidence generation procedure

1. Start from a requirement or acceptance checklist item.
2. Define the exact scenario and expected result before running it.
3. Run the actual command or manual procedure in a controlled environment.
4. Capture the result and relevant version/commit without sensitive data.
5. Have the named reviewer inspect the result.
6. Record failures, blocked checks, and fallbacks honestly.

No application evidence was generated by this setup because the implementation repositories and executable commands are unavailable.
